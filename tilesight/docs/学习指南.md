# TileSight 模型学习指南

这份文档解释这个模拟器**是怎么算的**，以及每个配置项在模型里起什么作用。读完你应该能看懂任何一份输出，并判断某个数字可信还是需要先校准。

英文的设计文档在 `docs/DESIGN.md`（公式和偏离论文之处），任务清单在 `docs/TASKS.md`，给 Claude Code 的约定在 `CLAUDE.md`。

---

## 1. 它是什么，不是什么

**是**：一个静态解析模型。输入形状、硬件参数、运行配置，用闭式公式算出时间。不需要 GPU，不跑模型，不跑 kernel。整模型一次评估约 0.4 秒。

**不是**：模拟器（不逐周期仿真硬件）、不是 profiler（不测量）、不是编译器（不生成代码）。

**能回答**：这个 kernel 卡在哪个资源上？换个 tile 会快多少？HBM 带宽加到 12 TB/s 值不值？加 64 MB 片上 buffer 有用吗？这张卡上这个模型的显存够不够？

**不能回答**：真实运行时的抖动、调度噪声、驱动行为、编译器的寄存器分配。

---

## 1b. 接口边界：GPU config 是输入

GPU 是**输入**，不是模型的一部分。`hw/schema.py` 声明了模型能看见的全部字段——99 个字段、15 个分区，每个都带类型、单位、默认值和标签：`spec`（照抄厂商数据）、`calib`（必须实测）、`policy`（建模选择）、`loss`（损耗系数，默认一律为零）。

参考文档由 schema 自动生成：`docs/CONFIG.md`，或者 `tilesight config --list`、`--md`、`--csv`。

三条规则保证边界干净，并且有测试强制执行：
1. 模型只通过 `hw.get(路径)` 取值，调用点不写字面默认值——字段缺失时从 schema 取默认，硬件知识只存在于一个文件里。
2. `engine/`、`kernels/`、`model/` 下的代码不得出现任何型号、厂商或架构名（注释除外）。
3. 每个预设都必须通过 `HardwareSpec.validate()`（未知字段、类型错误、缺必填项），新卡也用 `tilesight config --validate` 检查。

所以加一张新卡 = 写一个 YAML；加一个硬件**概念** = 在 schema 里加字段，再在模型里用它。

## 1c. 三个输入

模型有两份输入，各有独立 schema：

1. **GPU 配置**，两种等价写法：
   - 扁平形式（`hw/schema.py`）：数据手册视角，模型直接消费。`tilesight config --list`
   - slice 形式（`hw/slice_config.py`，42 个字段）：架构师视角——每个 shader core 里几个 tensor core、MMA tile 的 M/N/K 和几个 cycle、shared memory 和 GPR 是共享还是均分、一个 shader slice 几个 core 共享 L1、几个 memory slice（各自带 HBM + L2 port + DMA port，L2 可以为 0）、地址是线性还是按 N KB 交织、on-chip buffer 放什么、gmem 上下行读写带宽。`derive()` 会算出每个 tensor core 和 shader core 的 TFLOPS、整卡 PFLOPS 和各级总带宽，`to_hardware_spec()` 翻译成扁平形式。`tilesight gpu --file my_gpu.yaml`

   **Tile 策略也在这里**（`compute.tile_policy.gemm`、`compute.tile_policy.attn`、
   `compute.tile_policy.overrides`，tag `policy`）：填 `auto`（按算子形状自动搜索）或固定 tile
   的 JSON。这是"这张卡怎么算一个 GEMM/attention"的建模选择，跟具体跑哪个模型无关，所以不在
   workload 里，而是 GPU 配置的一部分。命令行用 `--set compute.tile_policy.gemm=...`，网页/API
   用 `hw_overrides`。
2. **Workload 配置**（`model/workload.py`，34 个字段）：单卡上的一层——attention 类型和维度、FFN/MoE、各种 dtype、phase/batch/seq。`tilesight config --workload`

模型真正的、也是唯一的入口是 `run(cur_gpu_config, cur_model_config)`（`model/runner.py`，包根目录也能
直接 `from tilesight import run`）：`cur_gpu_config` 就是上面第 1 点算出来的 `HardwareSpec`，
`cur_model_config` 是一个 `CurModelConfig`（打包了 `ModelSpec` 架构 + `RunConfig` 跑法）。**model 层不认识
"workload" 这个东西**——workload 只是构造 `cur_model_config` 的一种方式（`to_model_spec()` +
`to_run_config()` 把那份单层 dict 转成一个 `CurModelConfig`），转完之后就和 workload dict 没关系了。

网页向导（`tilesight serve` 后访问 `/`）就是按这两份输入分步的：选卡 → 编辑并校验硬件配置（含 tile 策略）→ 填 workload → 运行（进度条 + 实时日志显示 `文件:函数 → 算子`，卡住时一眼能看出来）→ 结果页。结果页有按配置画出的 GPU 架构图、时间去向、算子表，以及 Excel / CSV / PDF 下载。专家版单页界面移到了 `/expert`。

## 1d. 模型的三大块

模型内部按配置的结构组织：

```
shader slice ──┐
 tc cuda sfu   │               on-chip buffer          memory slice
 smem tmem     ├── switch ──►  每个 slice 旁边一块，  ──►  L2 端口 + DMA 端口 + HBM
 L1（slice 内） │               彼此互通，逻辑统一
 加载路径      └──────────────────────────────────────►（绕过 buffer 直连）
```

buffer 位于 shader slice 和 L2 **之间**，不是 L2 的下一层。一次访问要么走 switch 到 buffer（这时既不碰 L2 也不碰 HBM），要么绕过它直接去 memory slice。绕过不一定更快：`l2_MB: 0` 时端口直连 HBM，要付几百个 cycle 的延迟，模型会把这个和走 buffer 的代价放在一起比。

switch 是一条独立的资源通道，配的是**聚合带宽**，单个 slice 能用其中的 1/slice 份额，它自己也可能成为瓶颈。

**只建模一个 core，组成一个 slice，slice 之间是拷贝**。per-core 的通道（tc/cuda/sfu/smem/tmem）填的是单个 core 上的秒数；L1 是 slice 级资源，建模成"slice 数 × 每 slice 带宽"，这样同一 slice 内的 core 正好按数量分摊。slice 完全相同，所以用波次分解覆盖（论文 §3.4）：若干满波加一个尾波，尾波活跃 core 少、分到的共享带宽更多。

论文的核心机制不变：动作 DAG 和资源向量、流水线包络、tile 复用距离——只是复用距离现在跑的是按分区的确定性 tile cache，"哪个 tile 在 L2/L1"是事实而不是概率。

所有报告都按这三块汇总，而且有两个视角：`by_domain()` 拆的是**关键路径时间**，`activity_by_domain()` 看的是**各块有多忙**（不管是不是瓶颈）。加了 8 GB buffer 后前者显示 onchip_buffer 0%（它从不成为瓶颈），后者显示 6%（它确实在干活）。文本报告、网页结果页、Excel/PDF 列分组都用同一套命名。实测（K3 10 层，B300）：decode 是 memory 79% / shader_slice 16%，prefill 是 shader_slice 81% / memory 18%。

**flash attention 是一个选择**，不是内部假设。`attention.impl: flash | naive` 属于 workload 配置。8K prefill 上：flash 92.8 ms vs naive 226.4 ms（2.44 倍），attention 部分 14.6 vs 148.2 ms，naive 多用 70 GB 激活显存，而且瓶颈从 shader 翻到 memory。

## 2. 三层结构

```
模型层     每层多大 → 单卡上要执行哪些算子        model/
  ↓
Kernel层   每个算子 → tile 计划（grid、循环、动作） kernels/
  ↓
引擎       tile 计划 + 硬件 → 时间、瓶颈           engine/
```

这三层可以单独用：只想看一个 GEMM，就直接用 Kernel 层（网页的单卡模式）；想看整模型，就走全流程。

## 3. 硬件怎么描述：资源通道（lane）

硬件 YAML 被翻译成一组**通道**，每个通道是一种可以被占满的资源：

| 通道 | 来自配置 | 动作里填什么 | 速率 |
|---|---|---|---|
| `tc` | `compute.tc_dense_tflops[dtype]` | 一个 SM 上的秒数 | 峰值 × 效率 ÷ SM 数 |
| `cuda` / `sfu` | 对应峰值 | 一个 SM 上的秒数 | 同上 |
| `smem` / `tmem` | `memory.onchip.*` | 一个 SM 上的秒数 | 每时钟字节数 × 时钟 |
| `path:tma` / `path:lsu` | `load_paths.*` | 一个 SM 上的秒数 | 每 SM 的发射带宽 |
| `l2` | `memory.l2` | **字节** | min(总带宽 ÷ 活跃SM, 单SM上限) |
| `ddr` | `memory.ddr` | **字节** | 同上 |
| `sram` | `memory.sram`（可选） | **字节** | 同上 |

**两类通道的区别很重要**：per-SM 通道每个 SM 各有一份，所以直接写秒数；共享通道（L2/HBM）全卡共用，所以写字节，由引擎按当时**活跃的 SM 数**去分摊。这解释了一个常见现象：grid 填不满机器时，每个 SM 反而能分到更多带宽。

加一种片上存储或一条加载路径，只要在 YAML 里加一段，通道会自动出现，引擎代码不用改。

## 4. 引擎：一轮有多长

引擎处理的是一个已经数值化的 tile 计划：`num_blocks` 个 block，每个跑 `iters` 轮，每轮执行 `body` 里的动作。

### 4.1 波次划分

```
同时驻留 = SM数 × 每SM驻留block数
满波数, 尾波 = divmod(num_blocks, 同时驻留)
```
每波单独算。尾波活跃 SM 少，分到的 L2/HBM 带宽份额更大。**同一波内每个 SM 完全相同**，所以只建模一个代表性 SM——这也是为什么时间线只画一行 SM 而不是 160 行。

### 4.2 稳态一轮

```
R = max(  资源上界:  每SM并发block数 × max over 通道( Σ 动作占用 )
          缓冲递推:  关键路径 ÷ stages
          循环递推:  循环携带链 ÷ consumers  )
```

三项各自的含义：

- **资源上界**：同一条通道上的动作必须排队。哪条通道上的总占用最大，它就是瓶颈。
- **缓冲递推**：多缓冲的 load 要等 `stages` 轮前的消费者用完缓冲区才能复用，所以整条链除以 stages。
- **循环递推**：标了 `recurrent` 的动作（online softmax 的状态、attention 的累加器）必须等上一轮结果落下来，只能靠 `consumers` 个 warpgroup 乒乓来掩盖。

### 4.3 整个 kernel

```
一波时间 = T_pro + T_fill + iters × R + T_epi
T_fill   = max(0, 完整关键路径 − R)      # 第一轮暴露的延迟
kernel   = Σ(各波) + kernel 启动开销
```

### 4.4 延迟落在哪里

每个单元都有延迟（`compute.mma_latency_cycles` 等，按 cycle 配）。延迟**不改变吞吐**，只拉长依赖链，而它进不进稳态取决于依赖是不是循环携带的：

- **独立操作**（一次 tile MMA、一次多缓冲 load）：可以多条在飞，延迟只进 `T_fill`。MMA 延迟从 11 拉到 256 cycle，GEMM 只从 82.5 µs 变成 83.1 µs。
- **循环携带**（softmax 链）：延迟 ÷ consumers 直接成为 R 的下界。

## 5. Cache 模型：确定性的 tile 级模拟

论文用的 SDCM 回答的是"在这个复用距离下大概率命中吗"。但硬件管理的 L2 里，谁在缓存里是确定的，所以我们**直接模拟**，不用概率。

1. lowering 生成访问序列：按 swizzle 后的 block 顺序，覆盖 `waves_simulated` 个 wave（默认 2，这样跨 wave 的复用才看得见）。
2. L2 分成 `partitions` 个独立分区，每个分区装整块 tile，跑显式的替换策略（`policy: lru | fifo | mru`）。
3. 一个 tile 去哪个分区，**由它的地址决定**（走地址映射）。所以 layout 和 swizzle 直接影响均衡，二次幂跨距真的会把所有 tile 堆到一个分区。
4. 容量按字节算，不同大小的 tile 公平竞争。

输出不只是 miss 率，还包括**每个分区里还剩哪些 tile**、占用多少、驱逐了多少次。`tilesight kernel` 会打印，Figure 3 的 (f) 面板里也有。

实测（B300，4096³ FP8 GEMM）：命中率 93.8%；默认交织下所有常驻 tile 都在 partition 0，换成 `mode: hash` 后均匀分成 40/40/40/40。把有效 L2 从 83 MB 压到 1 MB 会产生 208 次驱逐。

**损耗是配置项，默认为零**。每级 cache 都有 `capacity_derate`，所有预设都是 **1.0**——默认不打折，模拟可以用满物理容量，不会有任何暗中的折扣。只有在有实测依据时才调低它：它承担的是 tile 级模拟没覆盖的东西（cache line 粒度、分区内冲突、其他 kernel 的流量、streaming 提示）。如果直接有实测的带宽-工作集拐点，用 `effective_capacity_MB` 覆盖（论文在 B200 级别上测到约 83 MB，相当于 126 MB 的 0.66，这个值现在只存在注释里）。

其他损耗系数同理：`efficiency.*` 缺省就是 1.0，`memory.queueing.coef` 缺省为 0。`--ideal` 开关（或 `HardwareSpec.lossless()`）一次性关掉全部损耗——效率因子、容量折损、排队、单 SM 上限、outstanding 限制——得到理论峰值基线。B300 上这些损耗合计：大 GEMM 1.14 倍、decode GEMM 1.24 倍、Kimi-K2 decode 1.26 倍（35.5 vs 28.2 ms）。

**L1 也是同样的建模方式**。配置在 `memory.l1`：`owner`（`sm` 或 `cluster`，Hopper/Blackwell 的 cluster 通过 DSMEM 共享，可用容量乘 `cluster_size`）、`capacity_KB`、`smem_carveout_KB`（tile 计划已经占走的 scratchpad，剩下的才缓存全局访问）、`cache_global_loads`、`capacity_derate`、`bytes_per_clk`、`latency_cycles`、`policy`。B300 是 (256−228) × 0.75 × 2 = 42 KB。

L1 是**私有**的，所以模拟的序列只是一个 SM 上那些常驻 block 的访问，不是整个 wave；而且只有真正经过它的路径才查（DMA 直接写 SMEM/LDS 的不查，由 `smem_direct` 决定）。L1 命中就不会到 L2 通路：1024×1024×512 的 BF16 GEMM 走 LSU 路径时命中 37%/12%，L2 流量从 16 KB 降到 12 KB；同一个 GEMM 走 TMA 则完全绕开 L1。

**片上 buffer 不是 cache**：它是显式管理的，按张量类别做确定性的容量分配，不存在概率。

旧的 SDCM 仍然保留（`memory.l2.model: sdcm`）用于对比。论文报告过它在 deep-K 场景偏乐观（82% vs 实测 43%），这也是我们改成确定性模拟的原因之一。

## 6. 地址模型

### 6.1 地址从哪来

模型层知道每层每个矩阵多大，所以地址就是一次分配：按执行顺序发放 2 MB 对齐的区间。`tilesight memmap` 能 dump 出来（Kimi-K2 是 548 块权重区间，141.7 GB）。

### 6.2 地址→单元的映射

`memory.addressing` 分两侧配置（L2 侧和内存侧是不同硬件）：

```yaml
addressing:
  addr_bits: 48
  l2:  {ports: 16, mode: interleave, granularity_KB: 1}
  ddr: {ports: 8,  mode: interleave, granularity_KB: 1}
```

三种模式：`interleave`（按粒度轮转）、`range`（48 位空间等分）、`hash`（交织前先异或折叠高位）。

`tilesight addrmap` dump 映射表，`--decode 0x...` 解码单个地址。

### 6.3 为什么要地址

分析**同时被访问**的那批 tile 散布得均不均匀。全部 tile 的地址集合与 layout 无关，layout 改变的是谁和谁同时活跃。实测（B300，16 slice，4096³ GEMM 一个 wave）：

| 配置 | 不均衡 | 等效 L2 带宽 |
|---|---|---|
| 1 KB 交织 | 1.33× | 75% |
| 2 KB 交织 | 2.00× | 50% |
| hash | 1.04× | 96% |

我们靠这个发现过一个真实问题：row-major 的 B tile 跨距 256 KB，正好是 2 KB × 16 slice 的整数倍，于是全部别名到 slice 0。

## 7. 内存系统的细节配置

```yaml
memory:
  l2:
    blocks: 4                      # 物理独立的 L2 块，各有自己的 load/store 端口
    ports_per_block: 1
    bytes_per_clk_per_port: 3072   # 块数 × 端口 × 宽度 × 时钟 会封顶总带宽
    line_bytes: 128
    sector_bytes: 32
  outstanding:
    per_sm_lines: 512              # 每个 SM 在飞的 cache line 数（类似 MSHR）
  dma:
    engines: 8
    per_l2_block: true             # 每块一个引擎，还是共享一个
    destination: smem              # smem | l2 | bypass
  l1:
    owner: sm                      # sm | cluster
    capacity_KB: 256
    cluster_size: 2
```

两个机制值得单独说：

**Little's law 上界**：`每SM带宽 ≤ 在飞行数 × line字节 ÷ 延迟`。这是为什么延迟受限的 kernel 加 HBM 带宽没用。实测影响很大：

| per_sm_lines | 每 SM 上限 | GEMM 时间 |
|---|---|---|
| 64 | 10 GB/s | 345 µs |
| 256 | 39 GB/s | 90 µs |
| 512 | 77 GB/s | 83 µs |
| 2048 | 180 GB/s | 82.7 µs |

**DMA 落点**：`smem` 表示搬到片上但字节仍过 L2 通路；`l2` 表示引擎填 L2、消费者再读（多一份 L2 写流量）；`bypass` 表示绕开 L2 通路。同一个 GEMM 分别是 82.7 / 131.4 / 82.5 µs，L2 占用 68% / 84% / 2%。

## 8. DMA 和普通 load 的区别

不只是带宽不同，是两种引擎：

| | DMA（TMA / TDM / buffer_load→LDS） | 普通 vector load（LSU） |
|---|---|---|
| 发射 | 一个描述符，不占发射槽 | 占 `cuda` 通道做地址生成 |
| 落点 | 直接写 SMEM/LDS | 先经寄存器，多一次 SMEM 穿越 |
| 寄存器 | 不占 | 占，压低 occupancy |
| 多播 | 支持（一次取，喂整个 cluster） | 不支持 |

所以 `cluster_m > 1` 的 tile 在 LSU 路径上直接判非法。

## 9. 模型层：从层尺寸到算子

`model/lower.py` 把每个 block 展开成单卡要执行的算子，同时处理并行切分。几个要点：

- **Attention**：DP 组内 TP 切 head；MLA 的 latent KV 在 TP 各 rank 上是复制的，不切。
- **MLA**：decode 用吸收形式（W_UK/W_UV 变成 per-head 的批量 GEMM，注意力跑在 576 维 latent 上），prefill 用展开形式。
- **MoE**：这是最值得看的一段。

```python
El        = E / ep                          # 本卡专家数
Tu        = tokens / tp                     # 去重后本卡 token
p_active  = 1 - (1 - topk/E)^(Tu*ep)        # 一个专家被选中的概率
active    = El * p_active                   # 实际激活的专家
M_per_exp = Tu*ep*topk / E / p_active       # 每个活跃专家的 token 数
```

Kimi-K2、8 卡：decode batch 8 时每卡 1 个 token、7 个专家激活、每专家 M=2；prefill 时每专家 M=1366。这几行解释了 MoE 的全部性能行为——小 batch 时每个激活的专家都要把整份权重读进来，M 极小，算力利用率接近零。

## 10. 怎么读输出

### 瓶颈归因分两层

- 粗粒度：通道名 / `latency` / `launch` / `net`
- 细粒度：`ddr:load:expert_weight`（资源:动作，动作名带 tensor）、`latency:softmax(sfu)`（关键路径上最重的节点及其主导通道）

### occupancy 那一列

`1/smem+regs` 表示每个 SM 只能驻留 1 个 block，同时被 SMEM 和寄存器限制。所有同时达到最小值的资源都会列出来。

### 时间线

一行一个通道，虚线分隔每轮。load 画在它执行的轮次，但标的迭代号是 i+stages-1——这就是软件流水的错开。

### Excel

一行一个 cycle，一列一个 unit，单元格是占用它的 tile（`A#7`），**颜色按迭代号**，所以同一个 tile 从 HBM 到 tensor core 颜色不变。addresses 页有每个访问的地址、L2 slice、HBM port。

### Figure 3 输出

`--fig3 out.html` 生成论文 Figure 3 的 (d)(e)(f) 三个面板：(d) 资源向量表 + DAG + 包络公式，(e) 时间线，(f) 单 tile 报告（延迟、利用率、命中率、重叠率）。

## 10b. 两个容易踩的坑

**扫 `sms` 必须联动算力**。YAML 里的算力是整卡峰值，引擎按 `峰值 ÷ sms` 得到每 SM 速率。所以单独把 `sms` 翻倍等于把每个 SM 削弱一半。`sweep` 现在会自动联动缩放 tc/cuda/sfu 峰值（`auto_link=False` 可关闭）。联动后 B300 翻倍 SM 只快 1.34 倍，因为瓶颈转到了 L2——这是对的。

**通信重叠要显式打开**。默认 `overlap_mode: none`，所有集合通信都是暴露的（偏悲观）。`stream` 表示能藏在同层后续计算后面，`two_batch` 表示两个 micro-batch 交替、能藏在整层计算后面，`manual` 是旧的标量。Kimi-K2 decode tp=2：不重叠 38.3 ms，重叠后 35.9 ms。

**通道接近饱和会有排队延迟**。`memory.queueing.coef` 按 M/D/1 的等待时间给延迟乘一个系数 `1 + coef·u/(1-u)`（有上限）。吞吐仍由资源项决定，所以这只影响填充期和循环携带链：decode GEMM 从 20.2 µs 变成 22.2 µs。

**集合通信超出快速域会分层**。group 大于 `network.nvlink.domain_size` 时，不是一条慢环路跑到底，而是节点内 reduce-scatter、节点间对 1/d 大小的分片做 all-reduce、再节点内 all-gather。之前按扁平模型算，16 卡 all-reduce 高估了约 5 倍（5040 µs vs 868 µs）。

## 11. 上手练习

```bash
# 1. 单个 kernel：看 tile 怎么影响瓶颈
tilesight kernel --hw b300 --kernel gemm --dtype fp8 --shape '{"M":4096,"N":4096,"K":7168}'
tilesight kernel --hw b300 --kernel gemm --dtype fp8 --shape '{"M":4096,"N":4096,"K":7168}' \
    --tile '{"bm":64,"bn":64,"bk":64}'          # 对比：会从 tc 瓶颈变成 l2 瓶颈

# 2. 整模型
tilesight run --model kimi_k2.hf --hw b300 --phase decode --batch 256 --seq 8192 --dp 8

# 3. 请求级：TTFT、TPOT 曲线、峰值显存
tilesight request --model kimi_k2.hf --hw b300 --batch 256 --dp 8 --prompt 8192 --output 4096

# 4. 硬件探索
tilesight sweep --model kimi_k2.hf --hw b300 --phase decode --batch 256 --seq 8192 --dp 8 \
    --param memory.ddr.bandwidth_TBps --values 4,8,12,16
tilesight buffer --model kimi_k2.hf --hw b300 --capacity 32768

# 5. 地址和映射
tilesight memmap --model kimi_k2.hf
tilesight addrmap --hw b300 --decode 0x11d40000

# 6. 网页（计算在本机，别人只要浏览器）
tilesight serve --host 0.0.0.0 --port 8000
```

建议的自学路线：先用练习 1 感受 tile 的影响，再读 `engine/reference.py`（只有 150 行，是整个模型的权威定义），然后读 `kernels/gemm.py` 看一个 tile 计划是怎么生成的。

## 12. 哪些数字可信，哪些不可信

**结构性结论可信**：谁是瓶颈、换 tile 的相对收益、带宽扫描的趋势、显存是否放得下。

**绝对数值需要先校准**。所有 YAML 里标 `[calib]` 的都是占位值，包括：各类效率因子、L2 有效容量和带宽、单 SM 取数上限、各单元延迟、DMA 发射带宽、L2 块数和端口宽度、outstanding 行数、网络的 α/β。`docs/TASKS.md` 的 Phase C 是校准套件的任务清单。

**AMD 侧更粗**：MI450 的 HBM 带宽和 FP8 峰值目前有互相冲突的公开来源，MALL 大小是猜的，wave64 occupancy 和 MFMA 指令表还没建模。

**已知会偏乐观**：deep-K 的 L2 命中率（论文自己报告过 39 个百分点的偏差）。
